How to read this page Each statement names a claim, a status and the evidence behind it. Status describes the current build, not an ambition. Ratings are intentionally absent.

Scope and method

SafeTransit is three pieces: a Django web dashboard, a Flutter Android app, and an ESP32 hardware kit. The host runs the dashboard and the two-model driver detector (MediaPipe Face Landmarker + EfficientDet-Lite0); the two ESP32-CAMs, the IR sensor node and the NEO-7M GPS post over the vehicle's Wi-Fi. The only outbound service is an optional SMTP account for OTP and alert mail.

Included

What this page covers

Driver and passenger video, drowsiness and behaviour analysis, driver profiles and scorecards, pre-shift identity, IR counting, GPS, alerts and clips, violation records, analytics, reports, accounts and backup.

Excluded

What is not claimed

Certified safety equipment, fare collection, accident prediction, cloud multi-tenant hosting, TLS/at-rest encryption, and any feature that exists only in the proposal.

Convention

How a statement works

A short claim, a status, then the evidence. Where a claim was not formally measured, that is stated instead of implied.

Boundary

One vehicle, one server

A single local Django server, one vehicle's hardware and two roles: Operator (admin) and Conductor. Multi-company tenancy is out of scope.

Functional suitability

The degree to which the system provides functions that meet stated and implied needs, correctly and completely.

01

Scope coverage

Implemented

The built system covers two live camera feeds, drowsiness and behaviour analysis, and a six-question pre-shift check with face/ID verification.

It also covers IR passenger counting, GPS and device health, buzzer/dashboard/email alerts, saved clips, analytics, reports and scorecards, violation records, driver profiles, accounts, OTP and backup.

Not in scope: fare collection, accident prediction, cloud multi-tenant hosting and a certified safety rating.

EvidenceDjango routes and templates expose each function; the demo clips show the camera, count, GPS and alert loop running on the bench build.
02

Drowsiness is measured; behaviour cues are heuristics

Limited

MediaPipe Face Landmarker runs on the host CPU. Eye openness (EAR), mouth openness (MAR), PERCLOS, closed duration, yawns and head pose feed a per-driver calibrated profile; a threshold crossing raises a stage and a 0–100 score. For behaviour, MediaPipe Hand Landmarker supplies hand geometry and EfficientDet-Lite0 supplies object labels (phone, bottle, cup). Phone call, phone texting, smoking, drinking and distracted cues are geometry heuristics, not trained classifiers.

LimitDrowsiness is the stronger signal. A hand near the mouth can be read as smoking while drinking or eating, and a head turn can be read as distracted. Three flags in a day block a new trip until midnight; the end-of-shift report rolls the events up per driver.
03

Passenger counting follows the door sequence

Implemented

Two IR beams sit across the doorway. Entry or exit is inferred from which beam breaks first; a 25 ms debounce and a 900 ms single-beam cooldown reject chatter. A beam held LOW for 8 seconds is marked stuck; AUTO mode falls back to the healthy beam, and both stuck pauses counting instead of inventing a number.

EvidenceThe sensor page exposes each beam's live level and stuck flag; the dashboard capacity meter reads the resulting count against 40 seats.
04

Pre-shift identity is checked, with fallbacks

Limited

The pre-shift flow asks a six-question self-assessment and a five-question knowledge quiz, then a face scan and, where a code is present, an ID barcode read. Face identity uses YuNet detection and ArcFace embeddings; a liveness step rejects a static photo. A confident match against an enrolled profile switches the active driver automatically and logs a “Driver changed” event; an uncertain match leaves the current driver unchanged. There is no OCR fallback for an ID without a readable barcode.

LimitIdentity depends on lighting, camera angle and a clean barcode. A damaged or barcode-less ID cannot be read by this build.
05

GPS and device health are live

Implemented

The NEO-7M posts latitude, longitude, speed, satellites, HDOP and altitude. The dashboard maps the fix with Leaflet, and the device page reports each camera, the IR node, the GPS and the buzzer. A stale or missing device is shown as offline rather than as a fresh value.

02

Performance efficiency

The performance relative to the amount of resources used, under stated conditions.

06

AI inference is CPU-only

Limited

All AI inference runs on the host CPU through MediaPipe, EfficientDet-Lite0 and OpenCV; there is no GPU or paid cloud call. Frame processing competes with the Django server and the database on the same machine. No formal FPS or CPU profile is claimed.

LimitFrame rate depends on host CPU, camera resolution and Wi-Fi. This build does not publish a benchmark.
07

The control path stays on the local network

Limited

Cameras and the sensor node post to the Django server over the vehicle Wi-Fi; the dashboard and phone poll the same endpoints. The control path does not depend on the internet. Video and sensor latency still depend on Wi-Fi congestion, camera firmware and host load.

EvidenceThe dashboard shows camera age and sensor age, so a stale value is visible; no cloud round trip is part of the path.
08

History is sized for one vehicle

Limited

MySQL stores passenger readings, camera status, GPS fixes, drowsiness state, behaviour events, alert clips, trips and accounts; PostgreSQL is supported through DATABASE_URL. The schema is migrated by Django. The design target is one vehicle, not a fleet-scale time-series load.

LimitNo large-volume load test is claimed. Retention and archival are manual.
03

Reliability

The degree to which the system performs specified functions under specified conditions for a specified period.

09

Device loss is visible and isolated

Implemented

Each device has an independent status. If a camera stops streaming, the detector reports NO_FACE and the dashboard marks the camera offline; if the sensor node or GPS stops posting, its card goes stale. Reconnect controls sit on the camera page. The rest of the dashboard keeps running.

10

A stuck beam does not freeze the pair

Implemented

An IR beam held LOW for 8 seconds is flagged stuck and excluded from pair counting; AUTO mode continues on the healthy beam. If both are stuck, counting pauses and the device page says so. A cleared beam re-arms after 500 ms.

EvidenceThe behaviour is enforced in the sensor firmware and reported through the device API; the dashboard surfaces the stuck state.
11

Backup and restore are explicit operations

Implemented

The backup API exports the database and dashboard records; the import path restores a previous file. The UI exposes backup and restore, and the project keeps database dumps under backups/. A restore is deliberate, not automatic.

EvidenceBackup/import endpoints and their tests exist. There is no off-site replication.
04

Usability

The degree to which the system can be used by specified users to achieve specified goals effectively, efficiently and satisfactorily.

12

The dashboard reads at a glance

Implemented

The first screen puts the two feeds, capacity, route, GPS and device health in one view. The active driver and the alert count are visible without opening a menu. The same information is available in the mobile app.

13

The phone finds the server without a manual

Implemented

The app probes mDNS for safetransit.local, scans the local subnet for port 8000, and remembers the last working address; a manual IP dialog is the fallback. Device setup walks through the hotspot, the Wi-Fi handoff and address discovery.

14

Status is written in user terms

Implemented

Status appears as “No face detected”, “Sensor connected & reporting”, “GPS connected & reporting”, “No active alert” and “Online/Offline”. Technical detail stays in the serial log or the API instead of being the only explanation.

05

Security

The degree to which the system protects information and data so that access is appropriate to the level of authorisation.

15

Accounts, OTP and roles

Implemented

Django authentication protects the dashboard; new accounts pass an emailed OTP and operator approval. Roles are Operator and Conductor, with operator-only management pages. CSRF protection is enabled for form posts.

EvidenceSession login, the OTP model, role checks and protected user-management routes are present in the Django app.
16

Media and camera feeds need a session

Implemented

Uploaded face photos and alert clips are served by an authenticated view rather than Django's public static handler. Camera feeds are proxied through the server, so a viewer needs a session. Hardware posts can carry an optional device key.

17

Transport and storage are LAN-grade

Limited

The dashboard and API run over plain HTTP on the local network; TLS is not terminated by the app. MySQL data is not encrypted at rest by the application, and the optional device key can be left empty. This suits a trusted bus/LAN deployment, not a hostile network.

LimitNo TLS, no at-rest encryption and no per-field access control. The deployment boundary is the vehicle's trusted network.
06

Compatibility

The degree to which the system can exchange information with other systems and perform its functions while sharing an environment.

18

Client coverage is Chromium-led

Limited

The dashboard relies on current browser features — Tailwind, Leaflet, fetch and the camera proxy — and has been exercised in Chromium-based browsers. No formal Firefox, Safari or small-screen matrix is claimed.

19

The companion app is Android-only

Limited

The mobile app is a Flutter Android build distributed as an APK, targeting Android 10 or newer. There is no iOS build, and the app expects the server on the same LAN.

20

Database and deployment options

Implemented

MySQL 8 is the default; PostgreSQL works through DATABASE_URL. Docker Compose and a Render-style deployment are included. The schema is single-tenant, so there is no per-company isolation.

07

Maintainability

The degree to which the system can be modified effectively and efficiently, including correction and improvement.

21

Responsibilities are separated

Implemented

The Django project separates models, views, API routes, camera and clip handling, backups and templates. The detector, behaviour rules and driver profile are separate Python modules. The Flutter app and the ESP32 firmware live in their own trees.

22

Tests cover the logic, not the whole rig

Limited

Unit tests cover the behaviour engine, drowsiness state and alert-clip import; Django tests cover camera setup, driver profiles, GPS status and mobile login. There is no CI pipeline, coverage target or full end-to-end hardware test in the repository.

08

Portability

The degree to which the system can be transferred from one environment to another effectively and efficiently.

23

The server can move hosts

Implemented

The server is a Python/Django app with requirements.txt, .env configuration, Docker Compose and a Render blueprint. Moving it means installing Python 3.12+, pointing it at MySQL or PostgreSQL, and running migrations; the LAN address changes, so the phone must rediscover it.

24

Hardware moves, but not invisibly

Limited

Cameras, beams, GPS and buzzer are off-the-shelf and can be moved between vehicles. Camera IPs and the sensor mapping are configuration, but mounting, beam alignment and Wi-Fi setup are manual; there is no auto-provisioning.

Overall and limits

These are the facts an evaluator should weigh when assigning a rating. They are not a recommendation.

Overall picture

SafeTransit is a working capstone prototype, not a certified safety product. Its strongest evidence is the local loop: camera/beam input becomes an alert, and the alert becomes a saved record on the same dashboard the phone reads. Its weakest areas are camera-dependent detection, heuristic behaviour labels, LAN-only security, an Android-only client and the absence of formal accuracy, load and cross-browser testing.

Strong evidence

  • Live driver and passenger feeds with the AI overlay on the operator dashboard.
  • IR door counting with ordered entry/exit and a stuck-beam fallback.
  • GPS, vehicle speed and device health on the same screen.
  • Buzzer, dashboard alert, saved clip and optional email in one event path.
  • Analytics, reports, violation records and driver scorecards after the shift.

Known limitations

  • Camera-dependent. Lighting, resolution, glare and Wi-Fi affect what the AI can see.
  • Heuristic behaviour cues. Phone, smoking and distracted labels can false-positive.
  • Barcode-only ID. An ID without a readable code cannot be read.
  • LAN-grade security. No TLS, no at-rest encryption, optional device key.
  • Android only. No iOS build for the companion app.

Evidence method

Evidence was gathered by inspecting the Django routes, views, models and templates; running the dashboard and the detector against the bench hardware; reviewing the recorded demo clips; and reading the project's unit and API tests. The TAM/UAT instrument is a separate study and is not scored on this page.

No formal accuracy, latency, soak, load or cross-browser benchmark is claimed. Where a statement depends on formal measurement, it is marked Limited and the missing test is named. No rating is assigned here; the evaluation form is the place for one.

Media note

The screenshots and clips come from the project's CPS folder. Demo faces belong to the project team. Source screenshots that showed a full driver roster were not used; where a name appears in a clip, it is part of the bench demo.
